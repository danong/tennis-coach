# P2 — JJ candidate adoption can block Tau workspace cleanup

- **Run:** `9caa1fad-e7b3-4deb-9a95-c91caef22e19`; Tau revision unavailable; JJ 0.45.1.
- **Expected:** After a verified candidate is independently duplicated into the app graph, reviewed, integrated, and given an approved disposition, `tau release` should dispose of the original run workspace or provide an adoption sequence that keeps its topology releasable.
- **Actual:** `tau release` returned `blocked-active-work` with `topology-violation`: “workspace successor is not the expected direct child; refusing disposal.” The candidate and workspace were retained.
- **Sanitized reproduction:** Run one verified JJ-isolated task. Create a separate adoption revision from its candidate using the documented `jj duplicate -r <candidate> -d <integration-base>` approach, then perform normal descriptions/bookmark moves and call `tau release`. JJ may rebase descendants, leaving the run workspace successor outside the finalizer's expected direct-child topology.
- **Impact:** P2 workflow friction: adopted work is safe, but disposable worker workspace cleanup is blocked and the ordinary graph retains candidate revisions/workspace.
- **Workaround:** Do not force abandonment. Preserve the adopted revision separately, record the blocked state, and defer release pending a topology-preserving adoption procedure.
- **Suggested regression:** An integration/adoption test where a candidate is duplicated onto a separate base and its original workspace can still be released; alternatively document an exact JJ adoption sequence guaranteed not to rewrite the workspace successor.
